# Templates & Resources Guide

How to author and produce the learner-facing **templates, downloadable examples, and reference cards** that the weekly content links to via `[TEMPLATE: ...]`, `[DOWNLOADABLE: ...]`, `[DOWNLOADABLE EXAMPLE: ...]`, and `[LINKED RESOURCE: ...]` markers.

The working list of artifacts to build lives in `templates-and-resources-to-create.md` at the project root. This guide governs how each one gets made.

## What this guide governs (and doesn't)

**Governs:** Visual style, brand styling, fillability conventions, file structure, naming, and production workflow for learner-facing template and reference artifacts produced as Word documents.

**Does not govern:** Rubric or assignment-description documents (those live in `rubrics/` and follow their own pattern), interactive HTML modules, or anything Riipen-branded that learners receive as a finished document (e.g., grading guides, frameworks). Templates are artifacts learners *own and fill in*; rubrics and frameworks are artifacts they *consume*.

---

## Core distinction: templates are learner artifacts, not Riipen documents

Rubrics, grading guides, and frameworks are Riipen-authored documents that travel with the course as-is. They wear full Riipen branding — logo top-right, Vancouver address, footer.

Templates are different. A learner downloads the template, types into it, saves it, and submits it as their own work. The artifact becomes theirs the moment they open it. Riipen's logo and corporate address have no place on it once it leaves the LMS.

**Practical rule:** templates use Riipen brand colors and fonts so they feel consistent with the course environment, but they drop the logo, address, and corporate footer. Learners shouldn't be submitting their team charter with "1200-555 West Hastings Street" on every page.

## File structure

```
templates/
├── weekly-planning-worksheet.md        ← source markdown
├── weekly-planning-worksheet.docx      ← generated, gitignored
├── team-charter.md
├── team-charter.docx
├── pre-kickoff-confirmation-message.md
├── pre-kickoff-confirmation-message.docx
└── ...
```

- Source `.md` is canonical and version-controlled.
- Generated `.docx` is gitignored (regenerated by anyone who needs it).
- One file per template — no consolidated docs.
- Filename = the slugified artifact name, no week prefix. Templates can be referenced from multiple weeks; the filename shouldn't pretend they belong to one.

## Brand styling

Inherited from `scripts/md_to_docx.py`. Same colors, fonts, and sizing as rubrics and design docs — the difference is what gets *omitted* (header, address, footer).

### Typography

All text uses **DM Sans** (this is what Riipen's actual document template uses; Crimson Pro is for marketing, not docs).

| Element | Size | Weight | Color |
|---|---|---|---|
| H1 / Document title | 17pt | Bold | Orange `#FF7C0A` |
| H2 / Section heading | 14pt | Bold | Dark Blue `#050C2A` |
| H3 / Subsection | 12pt | Bold | Dark Blue |
| H4 | 11pt | Bold | Dark Blue |
| Body | 10pt | Regular | Dark Blue |
| Small / instructional | 9pt | Regular | Grey `#ACACAC` |

### Color palette

| Role | Hex | Usage |
|---|---|---|
| Orange | `#FF7C0A` | H1 title, bullet markers, table header background, blockquote left border, link text |
| Dark Blue | `#050C2A` | Body text, H2–H4 headings, table cell text |
| Electric Blue | `#2454FF` | Reserved (not used in templates by default) |
| Green | `#18733E` | Reserved |
| Grey | `#ACACAC` | Table borders, instructional micro-copy, alt-row text |
| Light Grey | `#F5F5F5` | Alt table row shading, code block background |
| Burnt Orange | `#B54708` | Reserved (Canvas accessibility; not needed in docx) |

### Table styling

- Header row: orange `#FF7C0A` background, white bold DM Sans 10pt text.
- Alt rows: light grey `#F5F5F5` background (zebra striping).
- Borders: 1pt grey `#ACACAC` on all cell edges.
- Column widths: auto-calculated using sqrt scaling so long-text columns don't dominate.
- Cell padding: 30–40 twips top/bottom inside cells.

### What's omitted from templates (vs. rubrics/design docs)

- **No logo in header.** Pass `--no-header` (see workflow below).
- **No Vancouver address.** Same.
- **No "Riipen | riipen.com" footer.** Same.
- **Optional small footer credit:** if a credit is needed, a single-line grey 8pt "Riipen Career Catalyst — Template" centered in the footer is acceptable. Default is no footer.

## Fillability conventions

Templates exist to be filled in. The shape of "fillable" depends on the content type.

### Fillable table rows
Tables where each row is a placeholder for the learner's content. Header row defines the columns; data rows are blank or contain a one-word prompt.

```
| Task | When | How long | Notes |
|---|---|---|---|
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |
```

For a long fillable list, use 8–12 empty rows. Don't go overboard — learners can duplicate rows themselves.

### Prompt-and-answer tables (the working-agreement pattern)
A two-column table where the left column carries the prompt and italic hint, and the right column is the empty answer space. Used in the Team Charter for communication norms, contribution expectations, and similar working-agreement sections. Also reusable for any other "structured negotiation" template (e.g., Team Processing Agreement).

```
| Prompt | Your team's answer |
|---|---|
| **Primary platform for day-to-day coordination** *(Slack, group chat)* |  |
| **Response time expectations on weekdays** |  |
```

### Prose sections (the substantive-field pattern)

When a field's answer is substantive, heterogeneous, or open-ended, use an H3 heading with an italic prompt underneath and open prose space below. Don't force these into a table.

Use when:
- Each field can vary widely in length (one sentence to several paragraphs)
- The fields aren't parallel in shape (one might be a bulleted list, another a paragraph)
- The content is the substance of the document, not a quick-lookup attribute

```
### Confirmed scope

*The project's boundaries and focus areas. What's in scope? What's out?*



### Deliverables

*What the team is producing: format, length, audience...*
```

Used in the Kickoff Summary for the three "what the employer confirmed" fields, plus the catch-all "Other notes" section.

### Choosing between the two

The prompt-and-answer table is right when the answers are short, parallel, and benefit from being read together as a list. The prose-section pattern is right when each field is its own substantive piece of writing. If you find yourself wondering whether a table row can hold what the answer actually needs to be, switch to prose sections.

Most templates will use both: tables for the structured / quick-lookup fields (timeline, contacts, sign-off, structured items with type tags), prose sections for the substantive narrative fields, plus a catch-all "Other notes" section at the end so anything that doesn't fit a structured field still has a home.

### Fill-in lines for short fields
Use an underscore run for inline single fields when a table is overkill:

```
**Project name:** _________________________________________

**Submitted by:** _________________________________________
```

About 40–60 underscores reads as "fill this in" without dominating the page.

### Prompted bullet lists
For open-ended responses where structure matters more than length:

```
**Three things I'm prioritizing this week:**

1.
2.
3.
```

Numbered or bulleted, with the marker present but the line blank.

### Example rows in tables
When the format isn't self-evident, include **1–2 italicized example rows** in grey at the top of the table, followed by a separator note like `*Examples above. Your entries below:*` and then the blank rows. The Change Log and Revision Plan templates explicitly call for this (see the source list).

### Instruction blocks
Italicized grey 9pt instructions at the top of a section, set off from the fillable content. Used sparingly — usually one short paragraph in the opening "How to use this template" section, plus optional one-line hints inside each section.

## Standard structure

Most templates follow this scaffold. Sections marked **Conditional** appear only when relevant.

| # | Section | Purpose |
|---|---|---|
| 1 | Title (H1) | Document title in orange |
| 2 | How to use this template | 2–4 sentence intro: when to use it, what it produces, where it goes. Italic grey. |
| 3 | Header fields (Conditional) | Project name, team, date, etc. — fill-in lines |
| 4 | Main content | The fillable substance — table(s), prompted bullets, sections |
| 5 | Submission note (Conditional) | One line: where to submit / who it goes to. Only if not obvious from the course page. |

The "How to use this template" intro is the most commonly-missed section. Always include it — learners encounter templates outside the page that linked to them, so the template has to stand on its own.

## Production workflow

### 1. Author the markdown

Write the template as `templates/<slug>.md` following the structure above. Standard markdown — H1/H2/H3, paragraphs, tables, lists, italics, bold. Inline `**bold**` and `*italic*` are honored.

Frontmatter is optional and not currently used by the conversion script.

### 2. Generate the docx

```bash
python3 scripts/md_to_docx.py templates/<slug>.md --no-header --no-footer
```

- `--no-header` suppresses both the logo and the Vancouver address.
- `--no-footer` suppresses the "Riipen | riipen.com" footer.

Templates pass both. (These flags were added alongside the first template — see the script section in `CLAUDE.md`.)

Output: `templates/<slug>.docx` (gitignored).

### 3. Review

Open the docx in Word or Google Docs. Confirm:

- No logo or address in the header.
- Title is orange, headings are dark blue.
- Tables render with orange header rows and grey borders.
- Empty cells / fill-in lines are visible and intuitive.
- DM Sans renders (fallback shouldn't trigger on a typical machine; if it does, install DM Sans).

### 4. Iterate

Edit the `.md`, re-run the conversion. The docx is regenerated from scratch — there's no in-place edit pattern.

## Naming conventions

- **Source filename:** kebab-case, no week prefix. `weekly-planning-worksheet.md`, `team-charter.md`, `change-log.md`. (One exception: items that are clearly tied to a single moment in the course — e.g., `kickoff-summary.md` — keep their natural name without forcing a week number in.)
- **Document title (inside the file):** Title Case. "Weekly Planning Worksheet", "Team Charter", "Change Log".
- **Source-list ID:** when referencing a template in conversation or commits, use the number from `templates-and-resources-to-create.md` (e.g., "Template #2").

---

## Linking templates from weekly content

Once a template exists, replace the placeholder marker in the weekly content with a real link or download reference. The exact mechanism depends on how Canvas hosts the file — until that's confirmed, leave the marker as `[TEMPLATE: <name> — link TBD]` and add a tracking note.

Templates are intentionally agnostic about which week they live in. The Weekly Planning Worksheet is introduced in Week 1 but learners reuse it for fifteen weeks; the Team Charter is introduced in Week 1 but referenced again in Week 2's team formation and Week 9's processing session. Don't bake week-specific framing into the template body — let the page that links to it do that work.

## Where this fits with other guides

- **`scripts/md_to_docx.py`** — the conversion engine. This guide adds template-specific conventions on top of it; brand styling is inherited unchanged.
- **`guides/deliverable-page-template.md`** — governs the *pages that link to* templates. The pages explain when and why the learner uses the template; the template itself is the artifact they fill in.
- **`templates-and-resources-to-create.md`** — the working list of artifacts to build. This guide is the *how*; that file is the *what*.
- **`rubrics/`** — sibling folder. Rubrics and grading guides live there and follow the full-Riipen-branding pattern (logo, address, footer). Templates explicitly diverge from that.
